# Taffy 对照基准

NanaUI 布局的性能参照是 [Taffy](https://github.com/DioxusLabs/taffy) 0.11（Bevy、Dioxus、Zed 等使用的 Rust 布局引擎）。Taffy 每个节点只存样式、布局缓存和算出的盒子，算完就结束；它是「只做布局」能做到多快的基线。`perf/micro/taffy-reference` 在同一台机器上让两者排同一批盒子，回答三件事：

1. **参照是谁**：Taffy 0.11，同场景、同 CSS、逐盒校验结果相同。
2. **差距多少**：block、flex、grid 三种布局的冷布局、增量编辑、常驻内存与每盒指令。
3. **多出来的消耗换来了什么**：NanaUI 每个节点比 Taffy 多存、多做的东西，各自对应哪项能力，以及 Taffy 没有对应功能的那些能力本身花多少。

结论先说：flex 与 grid 的冷布局慢 1.4–1.6 倍，每盒指令只多 1.1–1.2 倍；按第四轮的拆账，把为增量编辑和公开几何留的三样（计划、意图事实、发布的 `LayoutResult`）关掉，flex 每盒正好落到 Taffy 的水平。差距是功能上的取舍，不是没追平。block 差得最多（11 倍），因为 Taffy 的 block 是一条很短的算法，而 NanaUI 的块容器和 flex 容器走同一套每节点的保留工作。

这是观察，不是门禁；数字随机器与负载变化，判断看倍数与去向。

## 运行

基准是独立的 workspace，有自己的 lockfile，不在根 workspace 里；Taffy 只是它的依赖，不进任何产品 crate。

```sh
cd perf/micro/taffy-reference
cargo run --release -- check              # 两个引擎逐盒比对（默认 100 行）
cargo run --release -- check 1000         # 21 001 盒
cargo run --release -- compare 100,1000   # block / flex / grid 对照，2 101 与 21 001 盒
cargo run --release -- features           # NanaUI 独有能力，默认 1000 行
ROUNDS=12 cargo run --release -- compare  # 取最小值的轮数（默认 8）
SHOW=1 cargo run --release -- features    # 加打 inline 编辑与滚动帧的计数和各阶段耗时
/usr/bin/time -l target/release/nana-taffy-reference reps flex nana 1000 5
                                          # 固定工作量，从外面读 instructions retired
```

## 口径

- **页面**：1280 px 宽的根下 N 行，每行 10 格，每格 0.25 px 内边距、里面一个 24 × 16 的叶子（`1 + N × 21` 个盒子，与 `perf/micro/stack-depth` 的 `wide` 同形）。block 页：行和格都是块；flex 页：根是列，行是 4 px 间距的行；grid 页：每行是 10 列 `1fr`、列间距 4 px 的网格。
- **同一份 CSS**：NanaUI 侧用 `Stack::from_layout` 逐字段写出与 Taffy 相同的样式，同一角色共享一份布局。块盒和 CSS 一样只写 `display: block`，`auto` 宽度撑满包含块，与 Taffy 相同。Taffy 关掉取整（NanaUI 保留小数像素）。`check` 逐盒比较页面坐标与尺寸：三种布局各 21 001 盒、带页眉的 flex 页 2 103 盒，相差超过 0.01 px 的都是 0 个。
- **冷布局**：NanaUI 是产品首帧的那次布局（`layout_document_for_viewport`，只布局，不含 Scene、命中与无障碍），Taffy 是 `compute_layout`。「建树 + 布局」从空树开始计。
- **增量编辑**：NanaUI 在产品帧里改（`RuntimeDocument::flush`），报布局阶段与整帧（含命中索引、无障碍、提取）；Taffy 是 `set_style`（它会像 `mark_dirty` 一样把节点和祖先标脏）加 `compute_layout`。
- **计时**：每一轮里两个引擎轮流跑、每轮交换先后，读最小值；整个程序跑两遍（8 轮与 12 轮）再取最小。release，aarch64 macOS，2026-11-09，机器负载 3–5。
- **指令**：进程内读 `proc_pid_rusage` 的 `ri_instructions`，即 `/usr/bin/time -l` 打印的 instructions retired，同样取各轮最小。与 `time -l` 交叉核对（`reps flex … 100` 跑 25 次减 5 次，除以 20 × 2 101 盒）：NanaUI 每盒 39.9 k（含释放），进程内建树 + 布局 38.3 k；Taffy 18.0 k 对 17.8 k。
- **内存**：布局后树常驻的堆（分配减释放），不是分配流量。
- **与「资源预算」里的数不同**：[资源预算](/reference/resource-budgets)里 21 001 盒的 1.24 µs / 盒、2 523 B、布局 23.3 k 条指令来自 `stack-depth` 的 `wide`，那一页用 `Stack::row` / `column` 预设（行按内容收缩、子项居中对齐等），指令数用整进程相减、含释放。这里的样式是与 Taffy 一一对应的 CSS，所以绝对值低一些，倍数可比。

## 差距

21 001 盒（每盒）：

| 布局 | 引擎 | 冷布局 | 建树 + 布局 | 常驻 | 布局指令 | 建树 + 布局指令 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| block | NanaUI | 0.99 µs | 2.03 µs | 2 399 B | 17.7 k | 37.7 k |
| block | Taffy | 0.09 µs | 0.19 µs | 1 252 B | 1.8 k | 3.6 k |
| block | 倍数 | 11× | 10.7× | 1.9× | 9.8× | 10.6× |
| flex | NanaUI | 1.00 µs | 2.04 µs | 2 399 B | 17.8 k | 37.8 k |
| flex | Taffy | 0.71 µs | 0.82 µs | 1 252 B | 15.7 k | 17.4 k |
| flex | 倍数 | 1.4× | 2.5× | 1.9× | 1.1× | 2.2× |
| grid | NanaUI | 1.39 µs | 2.43 µs | 2 638 B | 26.0 k | 46.0 k |
| grid | Taffy | 0.89 µs | 1.00 µs | 1 278 B | 21.3 k | 23.0 k |
| grid | 倍数 | 1.6× | 2.4× | 2.1× | 1.2× | 2.0× |

2 101 盒时（数据都在缓存里）冷布局 block 0.78 对 0.07 µs、flex 0.79 对 0.64 µs（1.24 倍）、grid 1.16 对 0.82 µs（1.4 倍）；常驻 2 692 / 2 930 B 对 1 256 / 1 283 B。

增量编辑，21 001 盒，中间一行一个叶子的 `min-height` 在 16 与 24 px 间来回（这一行变高，下面每一行都要移动），每次编辑：

| 布局 | NanaUI 布局阶段 | NanaUI 整帧 | NanaUI 指令 | Taffy 布局 | Taffy 指令 | 布局倍数 | 指令倍数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| block | 194 µs | 490 µs | 10.9 M | 37.8 µs | 0.82 M | 5.1× | 13× |
| flex | 206 µs | 513 µs | 11.2 M | 94.2 µs | 2.15 M | 2.2× | 5.2× |
| grid | 459 µs | 758 µs | 16.2 M | 99.2 µs | 2.25 M | 4.6× | 7.2× |

怎么读：

- **flex 与 grid**：每盒指令只多 10–20%，时间多 40–60%。多出来的时间主要是每个节点要读写的字节更多（大树上布局受内存约束，见资源预算「CPU 时间」的规模曲线），而不是多算了什么。
- **block**：Taffy 的 block 算法很短（每盒 1.8 k 条指令，是它 flex 的九分之一）。NanaUI 的块容器和 flex 容器每盒花的时间几乎一样：成本在每个节点都要做的保留工作（下一节），不在格式化上下文的算法。块容器还要判定每个子项怎样参与（行内级、浮动、`display: contents`）、记行盒与基线的回答，这些是 Taffy 的 block 不支持的东西。绝对差距是每盒 0.9 µs。
- **建树**：NanaUI 建树每盒约 1.04 µs，Taffy 约 0.1 µs，见下一节。
- **增量**：布局阶段慢 2–5 倍；整帧里另一半是命中索引、无障碍与提取，Taffy 没有这些。

## 多出来的消耗换来了什么

flex 页 21 001 盒，每盒。时间的比例来自[资源预算](/reference/resource-budgets)「CPU 时间」冷布局第四轮的逐项关掉再量（`wide` 页、只为拆账、关掉后结果不对），按这里的 1.00 µs 折算；各项不可相加，四样都关是 −28%。内存一列里「布局前的树」与「布局保留」是本基准量的，细项来自资源预算「常驻内存」的分配栈归因（同一页面形状，2026-11-05 至 11-09 各轮），是近似值。

| 多做 / 多存的 | 每盒 | 换来的能力 |
| --- | ---: | --- |
| 测量计划与容器计划（每个容器每遍都建，首次布局为下一帧准备） | 约 17%，≈ 0.17 µs；≈ 395 B（测量计划 244、容器计划表 151） | 增量编辑零测量：同一档内连续改尺寸不测、百万行里一行长高至多测 2 个、子节点列表编辑回放而不走全部子节点（9 条 `WorkCounters` 合同；只给单子节点容器不建计划就会变红，见资源预算第四轮） |
| 意图事实（测量时记下每个盒子的用尺寸取决于什么） | 约 10%，≈ 0.10 µs；≈ 120 B（意图表） | 失效收窄：一处改动只重排真正受影响的盒子 |
| 发布 `LayoutResult`（每个节点一份 280 B 的结构，加片段、部件、子节点放置、依赖的切片） | 约 20%，≈ 0.20 µs；≈ 614 B | 公开的几何合同：片段、部件、基线、溢出、滚动范围、包含块；Scene、命中、无障碍、IME 都读它 |
| 以上三项（两种计划、意图事实、发布）都关 | −28%，剩 ≈ 0.72 µs | 与 Taffy 的 0.71 µs 相当 |
| 其余保留表（盒子、放置、内边距、上下文、参照系、行盒记忆、计划条目） | ≈ 230 B | 相对几何（`abs = frame + local`）与行盒判定的保留状态 |
| 建树：组件、节点记录、样式驻留、挂载提交 | 1.04 µs 对 Taffy 约 0.1 µs；1 043 B（Taffy 整棵 1 252 B） | 组件模型与 `MutationQueue` 原子提交；`NodeRecord` 上的 `NodeSpace` 分类（2 B）让平移、命中、无障碍不必走子树；组件视图、交互与无障碍状态 |
| 产品帧的其余阶段：命中索引、无障碍、提取与 Scene | 首帧 0.18 + 0.26 + 0.61 µs；+1 897 B（产品帧后常驻 4 296 B） | 命中测试、无障碍树、GPU 场景；本基准没有再把这 1.9 KB 拆到三者之间 |

合起来：flex 冷布局里比 Taffy 多出的 0.29 µs，基本就是为增量编辑与公开几何留下的东西；布局保留的 1 356 B 里约 1.13 KB 是计划、意图与发布的结果。这些都关掉就失去增量合同和 `LayoutResult` 合同，所以不再作为「待追平」的差距，见资源预算「待办」。

## Taffy 没有对应功能的能力

只报 NanaUI 的数，同一台机器、同样取最小值（`features 1000`）：

| 能力与场景 | 成本 | 增量 / 查询 | 成本落在哪 |
| --- | --- | --- | --- |
| **inline 文本的换行与基线**：1 000 段，每段 400 px 宽，4 段文字（中英混排）加 2 个 inline-block，折成 3 行（7 001 盒） | 产品首帧 3.98 µs / 盒（布局阶段 1.02），4 789 B / 盒，68.4 k 条指令 / 盒 | 改中间一段里一个 run 的文字：布局 1.60 ms、整帧 1.90 ms、44 M 条指令 | nana-text 的整形与断行（TextShape 阶段）、行内记录、行盒记忆与基线；行数变了，下面 500 段只挪原点（测量 1 个、放置 505 个） |
| **float**：block 行里每格 `float: left`，行是 `overflow: hidden` 的 BFC，高度由浮动撑开（16.5 px，21 001 盒） | 0.97 µs / 盒，16.5 k 条指令 | 同一页不浮动、竖排：1.02 µs / 盒，17.7 k | 浮动排布本身不比竖排贵；支持浮动的成本已经在每个块容器的参与判定里，即上一节 block 的差距 |
| **sticky 与 fixed**：flex 页放进 800 px 高的滚动容器，每第十行 `sticky; top: 0`，另有 20 个 `fixed` 角标 | 首帧 2.88 µs / 盒（不带它们 2.85） | 滚动一次：整帧 6.32 ms、94.7 M 条指令；不带它们 5.48 ms、85.9 M；布局阶段 0 | sticky 在滚动投影之后贴住、由 Scene 放置，不写回布局；滚动不重排。这一帧的大头是无障碍（约 6 ms）与命中（约 0.8 ms），见下文「观察」 |
| **保留式相对几何下的移动**：页眉变高，下面装着所有行的列整体下移 | 列里 2 100 盒：布局 5.9 µs、整帧 13.6 µs、0.25 M 条指令；21 000 盒：5.8 µs、17.9 µs、0.35 M | 两种规模都只测 1 个、放 3 个盒子；Taffy 同一编辑 1.0 µs | 盒子存相对参照系的偏移，挪父节点只改它一个偏移，子树不重算，命中、无障碍、Scene 同样不走子树；成本不随被挪动的盒子数增长 |
| **命中测试与无障碍树**：flex 页产品首帧（21 001 盒） | 每盒：命中索引 0.18 µs、无障碍 0.26 µs、提取 0.61 µs；常驻 4 296 B（布局后 2 399 B） | 一次命中查询 0.16 µs；整棵无障碍树投影 0.17 µs / 节点 | 命中条目与无障碍节点都按本地坐标保留，平移只改根 |
| **深树不爆栈**：一串嵌套 flex 列，在 512 KiB 的线程上 | 200 层：NanaUI 整帧 794 µs，Taffy 布局 232 µs | 500 层：NanaUI 整帧 1 969 µs，Taffy 栈溢出 | 放置在线程栈上最多走 `SPAN` 层，测量与建树在剩余栈不足时换新栈段，见资源预算「栈」 |

## 观察

这些是本基准顺带量出来的，不是门禁，也不在这次改动里处理：

- **inline 段落的编辑跟着被挪动的段数走**：100 段的页上改一个 run 布局约 0.17 ms，1 000 段约 1.6 ms，测量只有 1 个、其余是只挪原点的段落；同样挪动 500 行的 flex 页改行高布局约 0.2 ms。每个被挪动的段落约 3 µs，比纯盒子行贵一个数量级。
- **大滚动容器的一次滚动是线性的**：21 001 盒时滚动一帧约 5.5 ms，几乎全在无障碍与命中阶段（裁剪更新 2 100 个），布局与提取不到 20 µs。
- **经 `Stack::from_layout` 的块盒不写宽度时按内容收缩**（已修）：显式 `display: block` / `flow-root` 的容器现在按 CSS 块布局排，`auto` 宽的块级子项撑满包含块，不读 `align_items`（`LayoutStyle::child_align_items`）；本基准改回只写 `display: block`，`check` 仍逐盒一致。同一处还修了只含浮动的块容器高度按竖排累加：浮动不再计入普通块的高度，BFC 包住打包后的浮动，float 一行不必再定高。改回自然写法后同机 A/B 的每盒布局指令：float 页 16.5 k → 17.4 k（测量时也打包浮动），竖排页 17.8 k → 18.0 k；上表的时间仍是改动前测的。
